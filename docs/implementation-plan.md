# План ночной реализации ComputeForGood

Цель — собрать и проверить локальную alpha на FastAPI, PostgreSQL, Redis, React и Socket.IO. К утру приложение должно показывать основные экраны и выполнять реальный цикл работы с задачей в базе данных. Этот план утверждён к исполнению пользователем 3 октября 2026 года; внешняя публикация в него не входит.

## Результат ночной работы

Пользователь открывает каталог, изучает контракт задачи, получает lease, отправляет checkpoint и submission. Другой пользователь выполняет независимое review. Приложение рассчитывает quorum для конкретного head SHA, а интерфейс показывает изменения без перезагрузки. Проверки выполняются на PostgreSQL и Redis, а не на подмене базы SQLite.

Локальные демонстрационные пользователи и проекты явно помечены. Тестовая регистрация PR и тестовое событие merge не являются реальными результатами на GitHub. Публичный alpha из спецификации требует настоящих проектов, внешних MCP клиентов, OAuth и реальных PR; эти показатели не входят в ночную приёмку.

## Архитектура

- Backend: FastAPI, SQLAlchemy, Alembic, PostgreSQL, Redis, python-socketio и официальный Python MCP SDK.
- Frontend: React, TypeScript, Vite, React Router, TanStack Query и socket.io-client.
- Фоновые задания: отдельный Python worker для expiry, outbox и очереди интеграций; для локальной alpha достаточно одного worker.
- PostgreSQL хранит пользователей, проекты, задачи, leases, permits, submissions, reviews, audit и события интеграций.
- Redis используется для рассылки Socket.IO между процессами и вспомогательных очередей. Потеря Redis не меняет владение задачами.
- REST и MCP используют один слой доменных операций. Socket.IO сообщает об изменениях после commit. При подключении и reconnect frontend заново получает актуальные данные через REST.
- Один web сервис и worker; отдельный frontend в разработке. Docker Compose запускает всю локальную среду.

Версии зависимостей фиксируются после успешной установки и проверки совместимости. SDK версии, перечисленные в исходной спецификации, не считаются подтверждёнными одной ссылкой в документе.

## Дизайн и экраны

Общий язык интерфейса — спокойная светлая рабочая панель: молочный фон, тёмный текст, зелёный акцент для полезной работы. Статусы риска имеют текстовые подписи и самостоятельные цвета. Шрифты системные; данные задач и SHA используют monospace. Контент интерфейса на английском для международного продукта, документация плана на русском.

Навигация: Discover, Projects, My activity, Reviews, Connect MCP. Moderation видна только оператору. В верхней панели есть индикатор соединения и переключатель демонстрационной личности для проверки независимого review.

| P0 | Главная | Предложение продукта, краткий цикл, переход к задачам и подключению MCP; демо-метрики подписаны |

## Распределение агентов

Одновременно работают ведущий и три агента. На первом этапе они готовят дизайн, доменную архитектуру и порядок сборки. После фиксации общего контракта переходят к реализации.

| Владелец | Файлы | Ответственность |
| --- | --- | --- |
| Ведущий | Корневые конфигурации, Docker Compose, README, docs, скрипты запуска | Контракт, окружение, интеграция, runtime, финальная проверка |
| Backend агент | backend/** | Модели, миграции, транзакции, API, auth, Socket.IO, worker, MCP |
| Frontend агент | frontend/** | Дизайн, React экраны, формы, API клиент, Socket.IO и адаптивность |
| QA агент | tests/** | Независимые HTTP и concurrency тесты, сквозной сценарий, отчёт дефектов |

Агенты не изменяют чужие зоны без сообщения ведущему. Миграции пишет только backend агент. Изменение контракта фиксируется в docs/api-contract.md и сразу сообщается frontend и QA. Интеграция идёт по готовности блоков, а не в конце ночи.

## Порядок работы

Оценки ниже — рабочий бюджет этапов, а не обещание длительности. При задержках сокращаются P1 экраны и декоративные элементы; атомарность claim и проверки прав остаются обязательными.

1. Подготовка среды и контракт, около 30–45 минут: структура, Compose, зависимости, схемы ответов, тестовые личности и seed. Проверка: healthy PostgreSQL и Redis, доступен /api/health, frontend запускается.
2. Параллельная реализация основы, около 1–2 часов: backend модели и чтение каталога; frontend shell и каталоги; QA инфраструктура тестов. Проверка: UI отображает данные из API.
3. Полный рабочий цикл, около 2–3 часов: claim, heartbeat, expiry, checkpoint, permit, submission, review и quorum. Frontend добавляет формы и жизненный цикл. QA проверяет конфликтующие запросы и права.
4. MCP и обновления, около 1–2 часов: инструменты используют те же операции, Socket.IO сообщает изменения, worker обрабатывает expiry и outbox. Проверка: два клиента видят изменение, reconnect получает актуальный snapshot.
5. Интеграция и исправления, около 1–2 часов: браузерный smoke, сборка frontend, тесты PostgreSQL, проверка Compose с чистой базой и документация.

Контрольные точки: инфраструктура → каталог из API → конкурентный claim → полный review цикл → MCP и Socket.IO → финальная приёмка. Завершённость каждого этапа определяется выполненной проверкой, а не количеством написанных файлов.

## Инварианты и тесты

- У задачи не бывает двух действующих canonical implementation leases; конкурентные claim дают одного победителя.
- Истёкший или чужой lease не может heartbeat, checkpoint, получить permit либо зарегистрировать canonical submission.
- Permit ограничен сроком, владельцем, задачей и lease; повторное использование не создаёт вторую submission.
- Автор submission не может review свою работу. Результаты других reviewers недоступны до собственного submit.
- Quorum считается для конкретного head SHA. Изменение SHA делает старые reviews неактуальными.
- Неразрешённый HIGH/CRITICAL finding блокирует успешный quorum. CRITICAL требует пяти независимых FRONTIER reviews и отдельного human решения.
- GitHub webhook проверяет подпись и delivery ID; повторная доставка не создаёт дубликатов.
- Merge credit начисляется один раз. Локальный demo merge отдельно помечен.
- Закрытые данные и комнаты Socket.IO доступны только разрешённым пользователям.
- После reconnect интерфейс получает состояние через REST и не считает потерянное событие подтверждением операции.

## GitHub и локальные данные

Ночная alpha работает без внешних credentials в явно включённом local demo режиме. Он доступен только локально и выключен по умолчанию для production. Нельзя копировать секреты из соседних проектов или считать demo login настоящим GitHub OAuth.

OAuth и webhook конфигурация описываются через переменные окружения. При наличии предоставленных credentials можно проверить настоящую интеграцию; без них отчёт явно показывает статус «не проверено». Демонстрационные URL и SHA не используются для внешних действий.

## Утренняя приёмка

- Приложение запускается из README, миграции и seed повторяемы.
- Основные экраны работают с настоящим API и PostgreSQL.
- Полный локальный сценарий выполнен под двумя независимыми пользователями.
- Есть результаты тестов конкурентного claim, expiry, self-review, quorum и webhook idempotency.
- Сборка TypeScript/frontend проходит; браузер проверен на desktop и mobile.
- README содержит URL, команды запуска, demo доступ, известные ограничения и список внешних настроек.
- Отчёт перечисляет выполненное, проверенное, пропущенное и оставшиеся дефекты. Число прошедших тестов берётся из реального запуска.

Для ночного выполнения компьютер должен оставаться включённым и без сна; Docker и рабочий сеанс должны оставаться доступными. Реализация идёт в текущем запуске. Регулярная автоматизация не создаётся.
