# Пять задач первого пилота безопасности

Проверено 13 октября 2026 года. Четыре внутренние задачи охватывают ComputeForGood, Deadtrace и Testence; одна внешняя — OSV-Scanner. Цель пилота — проверить путь от конкретной проблемы до принятого и выпущенного результата, включая затраты мейнтейнера и reviewer.

Это пять подготовленных контрактов, а не пять подтверждённых CVE или опубликованных заданий. В набор входят настройка приёма сообщений, проверка существующего исправления, два отдельных продолжения защиты диагностических данных и исправление отчётов security-инструмента. Три инженерных кейса сосредоточены в Testence: там есть свежие публичные основания; искусственно добавлять неподтверждённый дефект другого проекта ради разнообразия не нужно.

| ID | Задача | Подтверждённое основание | Условие начала |
|---|---|---|---|
| PILOT-01 | Приватный приём сообщений в CFG, Deadtrace и Testence | Reporting выключен у всех трёх; политики Deadtrace и Testence направляют в этот канал | Владелец определяет ответственного и включает канал |

| PILOT-03 | Убрать пароль из предупреждения Testence о параметрах | Компонентная проверка реальной функции воспроизвела значение в предупреждении | Согласованный baseline после PR 32 и автор исправления |
| PILOT-04 | Безопасный traceback по умолчанию в evidence Testence | Строка исходника с незарегистрированным секретом проходит sanitizer; этот пробел назван в PR 32 | Согласовать политику диагностических данных и воспроизвести полный путь |

## PILOT-01 Приватный приём сообщений в трёх репозиториях

**Результат:** исследователь может передать сообщение о безопасности по действующему приватному каналу, а публичная политика правильно описывает этот маршрут.

**Основание.** API `private-vulnerability-reporting` возвращает `enabled: false` для всех трёх репозиториев. [Deadtrace SECURITY.md](https://github.com/kiselas/deadtrace/blob/8aec2694cea6241d28a82975dbb77f8b85d6a35f/SECURITY.md) направляет туда исследователя; [Testence SECURITY.md](https://github.com/kiselas/testence/blob/c7a7949652758160c244e0be2f2a5ed5e02487e8/SECURITY.md) ещё и утверждает включение 21 сентября. У CFG корневого SECURITY.md на проверенном SHA нет.

**Объём:** включение GitHub private vulnerability reporting владельцем; создание `SECURITY.md` в CFG и точечное согласование политик Deadtrace/Testence. Это одна операционная задача с тремя проверяемыми результатами. Изменение прав участников, других настроек GitHub и кода приложений в объём не входит.

**Приёмка:**

1. Для каждого репозитория API возвращает `enabled: true`, результат записан с датой и именем репозитория.
2. Авторизованный пользователь без прав collaborator может открыть форму Report a vulnerability. Проверка завершается без отправки фиктивного отчёта.
3. В каждой политике указаны поддерживаемые версии, действующая ссылка, ответственный и согласованный владельцем срок первичного ответа. Новый срок не придумывается исполнителем.
4. Политика запрещает прикладывать реальные секреты и публично раскрывать ещё закрытую проблему; для доказательства достаточно минимального синтетического примера.
5. Утверждение Testence о старой проверке заменено актуальным подтверждением. Документирование временного обходного канала не считается включением reporting.

**Проверки:** `gh api repos/<owner>/<repo>/private-vulnerability-reporting` до и после, проверка формы под внешней ролью, review трёх документов. Прогоны кода не нужны. Публикация обновлённых политик и работающий маршрут завершают задачу; пакетный релиз не требуется.

**Владелец и риск:** kiselas выполняет административную часть; второй человек проверяет доступность формы. Риск документации предварительно LOW; настройка выполняется владельцем вне агентской очереди. Это устранение операционного пробела, без начисления «исправленной уязвимости».

## PILOT-02 Проверка и выпуск исправления Testence PR 32

**Результат:** уже написанное исправление утечек доходит до проверяемой версии пакета. Авторство patch сохраняется за текущим автором.

**Основание:** [PR 32](https://github.com/kiselas/testence/pull/32) открыт и имеет успешные проверки на указанном head. Он меняет выдачу raw trace/video, маскирование чувствительных полей, URL с паролем, обработку session secrets и права `auth.json` на Windows. Последний наблюдавшийся релиз — [v0.1.0a2](https://github.com/kiselas/testence/releases/tag/v0.1.0a2). Зелёный CI PR сам по себе не подтверждает выпуск исправления.

**Объём:** независимая проверка существующего PR, при необходимости замечания в его рамках, затем согласованный владельцем релиз. Создавать дублирующий implementation PR нельзя. Разрешённые артефакты — синтетические fixtures, отчёт reviewer, release notes и запись происхождения wheel. Новые случаи PILOT-03/04 принимаются отдельно.

**Приёмка:**

1. Reviewer проверяет именно принимаемый head SHA. Для исправляемых случаев есть наблюдение до/после: воспроизводится утечка на исходной версии и отсутствует после исправления; нормальное значение, например City, сохраняется.
2. Через реальный browser/CLI и export подтверждены: пароль/OTP не виден в ARIA, пароль URL не попадает в metadata, session canaries не попадают в ledger/export. Обычный `full` export и live Allure stream не содержат сырых trace/video/binary; режим `raw` требует явного выбора.
3. Windows-проверка `auth export` подтверждает закрытые права файла и отказ от создания при невозможности их установить.
4. Полный обязательный CI успешен на финальном SHA, все skips разобраны; skipped проверка нужного свойства не считается доказательством. Одни и те же неизменные проверки не повторяются локально и в CI без причины.
5. Из выпущенного wheel в чистом окружении повторяется короткий canary smoke. Записаны версия, SHA исходников, digest wheel, URL релиза и результат smoke. Только после этого статус «выпущено».
6. Release notes перечисляют исправленные поверхности и оставшиеся ограничения, включая source lines и node IDs. Нет обещания очистки произвольных секретов во всех данных. Для реальных ранее раскрытых credentials владелец отдельно принимает решение о ротации; выпуск пакета их не отзывает.

**Команды первого прохода:** после `uv sync --locked --extra dev --extra parallel --extra visual` и `uv run playwright install chromium` выполнить `uv run pytest -q tests/test_evidence_leaks.py tests/test_attachments.py tests/test_trace_video.py tests/test_redaction.py tests/test_redaction_policy.py tests/test_allure_stream.py tests/test_expect_request_and_auth_export.py`. Перед приёмкой — действующие gates из [CONTRIBUTING.md](https://github.com/kiselas/testence/blob/c7a7949652758160c244e0be2f2a5ed5e02487e8/CONTRIBUTING.md) и CI. Команды smoke установленного wheel фиксируются в release receipt вместе с выбранной версией.

**Владелец и риск:** kiselas отвечает за выпуск; reviewer с опытом browser evidence и credential handling не должен быть автором patch. Финальный инженерный риск ещё не утверждён, для планирования считать чувствительной ручной проверкой. Произвольный существующий PR сейчас нельзя импортировать в CFG как собственную реализацию: это отдельный ручной пилот review/release, без implementation credit задним числом. При HIGH/CRITICAL реальная выдача через CFG остаётся закрыта.

## PILOT-03 Пароль в предупреждении Testence о параметрах

**Результат:** собственное предупреждение Testence о небезопасном `parametrize` не повторяет чувствительное значение.

**Основание:** [_warn_about_allure_identity](https://github.com/kiselas/testence/blob/2fbd96e0100f4d5e027530a9c11453e084b8d811/src/testence/pytest_plugin.py#L577) обнаруживает чувствительное имя параметра и включает весь `item.nodeid` в предупреждение. Компонентный запуск этой реальной функции с синтетическим `password` подтвердил значение в warning. PR 32 оставляет sensitive parametrized IDs для дальнейшей работы.

**Baseline:** указанная ревизия PR 32 для исследования; реализация — от свежего main после интеграции или от отдельно согласованной ветки, чтобы не дублировать текущие изменения.

**Разрешённые пути:** `src/testence/pytest_plugin.py`, относящиеся к предупреждениям тесты в `tests/test_allure_compat.py` либо новый `tests/test_sensitive_parameter_warning.py`, короткое пояснение EN/RU в существующей документации. Переписывание pytest node IDs, контрактов identity и Allure history ID исключено.

**Приёмка:**

1. В отдельном pytest subprocess параметр `password` без безопасного `ids` вызывает предупреждение; сам синтетический пароль отсутствует в тексте предупреждения Testence.
2. Проверены также целочисленный `pin`, Unicode и строка с кавычками; параметр с обычным значением не порождает ложного security warning.
3. Диагностика сохраняет безопасное местоположение теста, имя параметра и подсказку задать нечувствительные `ids`; добавление явного безопасного ID устраняет это предупреждение.
4. Новый тест падает на baseline из-за присутствия canary и проходит на исправлении. Проверка относится именно к сообщению Testence: стандартный вывод pytest с исходным node ID не выдаётся за очищенный.
5. Результаты тестов, число collected cases, выбор через `-k` и идентичность Allure не меняются. Существующие warnings о дублирующих Allure ID продолжают работать.

**Проверки:** `uv run pytest -q tests/test_sensitive_parameter_warning.py tests/test_allure_compat.py tests/test_identity.py` после добавления нового файла; форматирование, Ruff, mypy и обязательный CI на принимаемом SHA. Никакого browser для короткой итерации не нужно.

**Владелец и риск:** kiselas — принимающий; автор и reviewer ещё назначаются. Предварительный риск LOW для ограниченного изменения диагностики. Завершение implementation — merge с доказательствами; завершение remediation — присутствие в выпущенном wheel. Эта задача не решает утечки node IDs из всех сторонних pytest reporters.

## PILOT-04 Безопасные диагностические стеки Testence

**Результат:** evidence по умолчанию сохраняет диагностический стек без строк исходного кода и локальных значений, которые могут содержать незарегистрированные credentials.

**Основание:** [_report_trace](https://github.com/kiselas/testence/blob/2fbd96e0100f4d5e027530a9c11453e084b8d811/src/testence/pytest_plugin.py#L1071) передаёт `longreprtext`; writer пропускает его через sanitizer. В компонентной проверке строка вызова `fill` с синтетическим, заранее не зарегистрированным паролем осталась в `error_trace`. Известный sanitizer секрет удалился — существующую защиту известных значений не следует ломать. Сам PR 32 явно выделяет test source lines как оставшийся случай.

**Политика на согласование:** безопасный traceback содержит имена функций, безопасные относительные пути, номера строк, тип исключения и уже очищенное сообщение; исходные строки и locals не сохраняются по умолчанию. Исключения из политики требуют отдельного явного режима. Не обещать автоматическое распознавание любого секрета в произвольном тексте исключения.

**Разрешённые пути:** `src/testence/pytest_plugin.py`, при необходимости `src/testence/evidence/writer.py`, новый `tests/test_traceback_privacy.py`, `tests/test_pytest_lifecycle.py`, `tests/test_export.py`, `tests/test_export_junit.py`, соответствующие документы EN/RU. Добавление режима raw diagnostics и изменение общего identity-контракта не входят в первую итерацию.

**Приёмка:**

1. На baseline отдельный синтетический failing test воспроизводит путь от строки исходника до `error_trace` в сохранённом ledger и экспорте. Если полный путь уже защищён текущим main, реализация снимается, остаётся воспроизводимый результат проверки.
2. После изменения canary из исходной строки и locals отсутствует в ledger, pack, Allure/JUnit export, HTML report и live stream, где доступны эти diagnostics. Для каждого пути есть явный результат, без автоматического распространения вывода с одного exporter на остальные.
3. Сохраняются статус failed/broken, различие assertion/infrastructure error, безопасные frame/function/line и полезное очищенное сообщение. Пустой traceback или замена всех ошибок на success не принимаются.
4. Проверены setup, call, teardown и chained exception; результат одинаков при обычном запуске и xdist. Старые артефакты: либо безопасная обработка при экспорте, либо явный отказ с причиной; их нельзя молча считать очищенными новой политикой записи.
5. Тест известного секрета и несекретный контроль продолжают проходить. Регрессии PILOT-03 и PR 32 сохраняются. У документации и metadata фактическая политика совпадает.

**Проверки:** короткий цикл `uv run pytest -q tests/test_traceback_privacy.py tests/test_redaction.py tests/test_redaction_policy.py`; затем lifecycle и export suites, xdist-ветка сценария и обязательный CI. Только синтетические тесты и временные каталоги. Глобальный полный прогон — один раз на финальном SHA, если свежего подходящего CI ещё нет.

**Владелец и риск:** решение о политике принимает kiselas, reviewer должен понимать pytest reporting и evidence privacy. Предварительный риск NORMAL, окончательная оценка после полного воспроизведения и выбора решения; при повышении до HIGH агентская выдача запрещена. Зависит от согласованного baseline PR 32. Выпуск пакета учитывается отдельно от merge.

## PILOT-05 Дубли SARIF в OSV Scanner

**Результат:** один и тот же finding не создаёт несколько одинаковых результатов только из-за нескольких advisory aliases; отдельные пакеты и места обнаружения сохраняются.

**Основание:** [issue 3093](https://github.com/google/osv-scanner/issues/3093) открыт и не назначен. На закреплённом SHA карта в `internal/output/result.go` связывает несколько IDs с одним объектом группы, а `internal/output/sarif.go` итерирует все IDs. Разбор актуального `sarif_test.snap` выявил три alias-сценария с двумя полностью одинаковыми results вместо одного. Контроль двух разных source locations имеет два различных results и должен сохраниться.

**Действующая чужая работа:** автор issue pmig и участник Denimworld12 уже выразили интерес; [PR 3122](https://github.com/google/osv-scanner/pull/3122) закрыт без merge с требованием соблюдать порядок внесения изменений. [CONTRIBUTING.md](https://github.com/google/osv-scanner/blob/f455353546889009663c1f8b640d5880a01c889a/CONTRIBUTING.md) требует назначения до начала PR и CLA. Ни приглашение в пилот, ни назначение пока не получены. Не открывать ещё один competing PR; при продолжении существующим автором предложить проверку только после отдельного согласования. Готовый patch другого автора не становится нашим вкладом.

**Разрешённые пути после назначения:** `internal/output/sarif.go`, `internal/output/sarif_test.go` или новый `internal/output/sarif_dedup_test.go`, соответствующие snapshots. `result.go` — только если reviewer подтвердит необходимость. Версионный resolver, обнаружение уязвимостей, severity policy и сетевые интеграции вне задачи.

**Приёмка:**

1. Детерминированный офлайн fixture с одним пакетом, одним source и двумя алиасами выдаёт один SARIF result. Новый assertion падает на baseline и проходит после исправления; одного обновления snapshot недостаточно.
2. Два разных пакета или версии сохраняют отдельные results даже с одинаковым advisory. Один пакет в двух разных source locations даёт два findings.
3. Разные advisory groups не сливаются. IDs/aliases, severity, messages и fingerprints сохранены; порядок результатов стабилен при перестановке входных aliases.
4. Пустой input, один advisory и случаи без CVSS остаются корректны. Табличный/JSON результат не меняется вне согласованного устранения дублей SARIF.
5. Diff snapshots объясняет каждый удалённый result как дубль; отдельные реальные findings не пропадают. Число rules не используется как замена числу findings.
6. Мейнтейнер принимает PR. Исправление связано с конкретным тегом/релизом OSV-Scanner; если upstream ещё не выпустил его, статус остаётся «принято, ожидает выпуска».

**Проверки:** Go `1.27.0` по текущему `go.mod`; короткий цикл `go test ./internal/output/... -run TestPrintSARIFReport -count=1`, затем `go test ./internal/output/... -count=1`, `go vet ./internal/output/...`. Финальные checks по upstream: `make test VCR=ReplayOnly` и `./scripts/run_lints.sh`, плюс требуемый upstream CI. Если для snapshot нужен `make test SNAPS=true`, после генерации повторить проверки без режима обновления. Не обращаться к чужим target-системам; fixtures и записанные ответы достаточны.

**Владелец и риск:** назначает upstream maintainer; author/reviewer ещё не подтверждены. Предварительный риск NORMAL: ошибка дедупликации может скрыть отдельное предупреждение. Это исправление security tooling, а не устранённая уязвимость сканируемых пакетов. До назначения, подтверждения CLA участником и утверждения контракта статус `WAITING_UPSTREAM`, `dispatch_allowed=false`.

## Порядок выполнения и измерение результата

Начать с PILOT-01 и независимого review PILOT-02. После согласования baseline выполнять PILOT-03, затем PILOT-04; их изменения касаются одного pytest plugin, поэтому параллельные несогласованные правки нежелательны. Внешняя задача ждёт upstream и не задерживает внутренние работы. Успех внутренних задач ещё не доказывает внешнюю востребованность.

Для каждого кейса записывать: момент согласования scope, старт, первый пригодный для review SHA, время первого review, merge и исправленный выпуск; отдельно активные минуты автора, reviewer и мейнтейнера, время ожидания и стоимость исполнения. Для PILOT-01 конечное событие — проверенный канал и опубликованная политика. Для PILOT-02 считать вклад проверки/выпуска отдельно от уже выполненного написания patch. Для остальных фиксировать также откаты и повторные регрессии после выпуска; отсутствие наблюдений не означает их отсутствие.

Итерации используют минимальный воспроизводящий сценарий. Приёмка требует актуальные обязательные проверки на том же SHA; кэш зависимостей допускается, перенос результата проверок со старого patch — нет. Требуемый skipped тест оставляет соответствующее свойство непроверенным.

Превращение карточки в доступную CFG-задачу требует верифицированного проекта, определённого автора/lease, окончательного риска, reviewer и публикации владельцем. Предлагаемые риски выше не заменяют это решение. Реальные HIGH/CRITICAL закрыты текущей политикой; обхода для security-пилота нет. Административная задача и проверка существующего PR выполняются вручную, пока нет соответствующего маршрута платформы.
