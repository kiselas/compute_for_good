# Самостоятельная проверка пилота безопасности

Внутренние улучшения можно воспроизводить, исправлять и выпускать без ожидания внешних участников. Автоматические проверки дают доказательства поведения; авторская самопроверка не становится независимым человеческим review или подтверждением спроса внешнего проекта.

## Воспроизведение известных случаев

Из корня CFG:

```powershell
uv run --with-editable backend --with-requirements tests/requirements.txt python scripts/reproduce-security-pilot.py
```

Команда загружает два публичных файла Testence на закреплённом SHA `2fbd96e0100f4d5e027530a9c11453e084b8d811`, выполняет компонентные проверки реальной функции warning и sanitizer с синтетическими данными. GitHub CLI должен иметь доступ к публичному репозиторию. Результат сохраняется в `artifacts/security-pilot-baseline/security-pilot-component-probes.json`; загрузки имеют таймаут.

Успешное завершение означает, что известный baseline воспроизведён: canary присутствует в предупреждении и незарегистрированной строке исходника, а положительные контроли redaction работают. Это не проверка исправленного Testence и не полный pytest → ledger → export сценарий. Изменение upstream main не меняет исторический baseline.

Для приёмки PILOT-03 и PILOT-04 новые регрессии должны падать на старом коде и проходить на исправленном, сохраняя несекретный контроль. Затем проверяются реальные ledger, exporter и installed wheel согласно [контрактам](seed/2026-10-13/security-pilot-contracts.md). Исправления в Testence выполняются в его checkout с его обязательными проверками; CFG не выдаёт себе фиктивный contribution за ручную проверку чужого PR.

## Проверки изменений CFG

```powershell
./scripts/verify.ps1
./scripts/verify.ps1 -Mode full
```

Первый профиль запускает быстрые offline/backend и frontend проверки. Полный профиль нужен перед выпуском изменений приложения; одинаковые успешные прогоны не повторяются без нового изменения или основания. В каждом отчёте фиксируются версия профиля, SHA, команды и результаты. Регрессии выпускного gate выполняются offline в `tests/test_deploy_ci.py`: другой SHA, чужой workflow/repository, незавершённый или failed CI и движение main должны блокировать выпуск.

Автоматический deploy проверяет конкретный triggering CI run через API и принадлежность `ci.yml`, избегая задержки индекса списка. Ручной deploy ограниченно ждёт успешный main push run того же SHA. При ошибке API, истечении времени или отсутствии точного успеха выпуск прекращается до публикации образов. Перед SSH выполняется дополнительная проверка текущего main.

## Следующие внутренние работы

1. Включить и проверить disclosure route в собственных репозиториях, согласовав фактические сроки ответа владельца.
2. Проверить существующий Testence PR 32 и installed-wheel результат, сохраняя происхождение patch.
3. Выполнить отдельное исправление warning, затем безопасного traceback с тестами до/после. Их критерии уже подготовлены.

Внешний OSV кейс остаётся дополнительным экспериментом и не задерживает эту последовательность. Его локальное воспроизведение возможно, но назначение и принятие upstream являются отдельными событиями. Ограничение HIGH/CRITICAL выдачи CFG сохраняется; ручная работа владельца не требует его отключения.
